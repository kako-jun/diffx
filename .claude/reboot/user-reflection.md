# 失敗原因と改善策 - ユーザー自己分析

作成日: 2025年11月14日

## 🚨 失敗原因

### 1. 3プロジェクトの同時進行と過度な共通化
**問題**:
- diffx, diffai, lawkit という3プロジェクトを兄弟として扱った
- 共通化をやりすぎて複雑化した
- 同時に進めようとして全てが中途半端になった

**本来あるべき姿**:
- diffxはほか2つから使われる立場
- diffxを先に確定して品質を高めるべきだった
- 依存関係: diffai/lawkit → diffx

**影響**:
- 3プロジェクト全てが不安定に
- 共有CI/CDシステムの崩壊
- どれも完成しない状態

### 2. モノレポ運用の失敗
**問題**:
- diffxはRust製だが、npm版、Python版が作れると知った
- モノレポで運用したのがまずかった
- 3×3 = 9個の組み合わせを1つのリポジトリで管理

**本来あるべき姿**:
- 3×3のリポジトリに分けるべきだった
```
diffx/
  diffx-rust/
  diffx-js/
  diffx-python/

diffai/
  diffai-rust/
  diffai-js/
  diffai-python/

lawkit/
  lawkit-rust/
  lawkit-js/
  lawkit-python/
```

**影響**:
- リポジトリ構造が複雑すぎる
- ビルド・テスト・リリースが管理困難
- 一部の変更が全体に影響

### 3. 開発ツールの知識不足
**問題**:
- huskyなどコミット前のlint、整形の知識がなかった
- MCPに関する知識がなかった
- 後から知って追加しようとした

**改善策**:
- 今からは活用したい
- Git hooks (husky/pre-commit)を最初から設定
- MCPの理解を深めて適切に活用

**具体的なアクション**:
```bash
# huskyのような仕組みを導入
- コミット前: cargo fmt, cargo clippy
- プッシュ前: cargo test
- 自動化で品質担保
```

### 4. Claude Codeのコンテキスト管理の理解不足
**問題**:
- Claude Codeのコンテキストがどの程度まで耐えられるか知らなかった
- コンテキストが劣化するという習性を知らなかった
- 過度な期待をして、実装漏れが増えた

**影響**:
- 長いセッションで品質低下
- 実装したつもりが実装されていない
- バグの増加

**改善策**:
- コンテキスト残量を常に監視
- 前提条件のドキュメントを毎回読み込ませる
- コンテキスト残量が十分な状態でのみ実装依頼
- 長いセッションは避け、適切に区切る

**具体的なルール**:
```
- セッション開始時: 必ず前提ドキュメント読み込み
- 大きな実装: コンテキスト70%以上を確保
- コンテキスト30%以下: 新セッション開始を検討
- 実装後: 必ず動作確認（AIの言葉を信じない）
```

### 5. 多言語ドキュメントの作成タイミング
**問題**:
- READMEやdocsを最初から3ヶ国語作ろうとした
- README.md, README_ja.md, README_zh.mdを同時更新
- 管理負担が大きすぎた

**本来あるべき姿**:
- README_ja.mdだけを基本とする
- 十分に完成した後、他言語を作るべきだった
- まずは母語（日本語）で完璧に

**改善策**:
```
Phase 1: README_ja.mdのみ作成・完成
Phase 2: プロジェクト成熟後、README.md（英語）作成
Phase 3: 需要が出てから README_zh.md（中国語）作成
```

### 6. 過度なドキュメント充実化
**問題**:
- リリースページやREADMEを充実させすぎようとした
- 詳細すぎる説明、多数のバッジ、完璧な例
- ドキュメント作成に時間を取られすぎ

**本来あるべき姿**:
- シンプルで良かった
- 必要最小限から始める
- ユーザーフィードバックで追加

**改善策**:
```markdown
# 最小限のREADME構成
1. プロジェクト説明（1-2行）
2. インストール方法
3. 基本的な使い方（1-2例）
4. リンク（ドキュメント、リポジトリ）

これだけで十分。
```

### 7. テスト戦略の失敗
**問題**:
- ユニットテストと統合テストを同時にやろうとした
- 全体像を把握できなくなった
- テストが失敗しても原因特定が困難

**本来あるべき姿**:
- まずユニットテストを徹底的に通す
- その後、統合テストに進むべきだった
- 段階的なテスト戦略

**改善策**:
```
Phase 1: ユニットテスト100%通過
  - 各関数・モジュールの単体テスト
  - cargo test で全て成功

Phase 2: 統合テスト追加
  - モジュール間の連携テスト
  - CLI動作テスト

Phase 3: E2Eテスト追加
  - 実際のユースケーステスト
  - パッケージインストールテスト
```

### 8. シンボリックリンクの罠
**問題**:
- シンボリックリンクを使うべきでなかった
- `github-shared -> ../.github` のようなリンク
- 環境依存、Git管理の問題、デバッグ困難

**影響**:
- CI/CDでパスが解決できない
- ローカルでは動くがGitHub Actionsで失敗
- 複雑性の増加

**改善策**:
- シンボリックリンクは使わない
- 必要なファイルは直接コピー
- または、明示的なパス指定

### 9. Rustクレート化の理解不足
**問題**:
- Rust製を他から取り込む場合はクレート化しないと取り込めない
- 手段を絞るべきだった
- モノレポ内での参照方法の混乱

**改善策**:
```
明確なルール:
1. 共通ライブラリ = クレートとして公開（crates.io）
2. プロジェクト固有 = モノレポ内でpath指定
3. 中間は作らない（複雑化の原因）

例:
diffx-core = crates.ioに公開
diffai, lawkit = diffx-coreをcrates.ioから取得
```

### 10. AIの実装嘘問題
**問題**:
- AIができるというから嬉しくなって全部実装してと依頼
- 実は実装していないのに「実装した」という嘘をつかれる
- リリース後に気づく

**影響**:
- バグの増加
- ユーザーに迷惑
- 信頼性低下
- 修正作業の増加

**改善策**:
```
必須ルール:
1. AIの報告を信じない
2. 実装後、必ず動作確認
3. テストを通す
4. 小さな単位で確認

具体的な確認方法:
- cargo build で確認
- cargo test で確認
- 実際にCLIで動かして確認
- 期待される出力を確認

「実装した」 ≠ 「動く」
```

### 11. コンテキスト管理の失敗
**問題**:
- 前提条件のドキュメントを毎回AIに読み込ませなかった
- コンテキスト残量が少ない状態で実装させた
- 品質低下・実装漏れの増加

**改善策**:
```
セッション開始時の必須チェック:
1. コンテキスト残量確認
2. 前提ドキュメント読み込み
   - CLAUDE.md
   - 関連する.claude/内のファイル
   - 該当するREADME

実装依頼時の必須条件:
- コンテキスト残量 70%以上
- 前提ドキュメント読み込み済み
- 実装範囲を明確に指定
- 小さな単位で依頼

実装後の必須確認:
- 実際にビルド
- 実際にテスト実行
- 実際に動作確認
- AIの報告だけで判断しない
```

## 📊 失敗パターンの分類

### Type A: プロジェクト設計の失敗
- 3プロジェクト同時進行
- モノレポ構造
- 依存関係の設計ミス
→ **影響: 大、修正: 困難**

### Type B: 開発プロセスの失敗
- テスト戦略
- ドキュメント作成タイミング
- リリース過多
→ **影響: 中、修正: 可能**

### Type C: ツール・知識不足
- husky/pre-commit
- MCP
- シンボリックリンク
→ **影響: 中、修正: 容易**

### Type D: AIとの協働失敗
- コンテキスト管理
- 実装嘘問題
- 過度な期待
→ **影響: 大、修正: 習慣化が必要**

## 💡 根本的な問題

### 複雑性への誘惑
すべての失敗に共通:
- 「理想的なシステム」を追求した
- 「完璧な構造」を目指した
- 「将来の拡張性」を優先した

結果:
- 複雑すぎて管理不能
- 現在の完成を犠牲に
- モチベーション低下

### 段階的アプローチの欠如
すべての失敗に共通:
- 同時に多くを達成しようとした
- 段階を踏まなかった
- 完成前に次の計画

結果:
- どれも中途半端
- 優先順位の喪失
- リソース分散

## 🎯 改善策の原則

### 1. シンプルさの徹底
```
- まずは1プロジェクト（diffx）に集中
- 1言語（日本語）のドキュメント
- シンプルなCI/CD
- 最小限のテスト
```

### 2. 段階的アプローチ
```
Phase 1: diffx単体を完成
Phase 2: ユーザー獲得
Phase 3: フィードバック対応
Phase 4: 次のプロジェクト検討

各Phaseの完了を確認してから次へ
```

### 3. AIとの協働ルール
```
セッション前:
- コンテキスト残量確認
- 前提ドキュメント読み込み

実装依頼:
- 小さな単位
- 明確な範囲
- 十分なコンテキスト

実装後:
- 必ず動作確認
- AIの報告を信じない
- テストを通す
```

### 4. 品質担保の自動化
```
Git hooks:
- pre-commit: fmt, clippy
- pre-push: test

CI/CD:
- プッシュ時: 全テスト
- シンプルで理解可能
```

## 🚫 やってはいけないこと

### 絶対に避ける
```
1. 複数プロジェクト同時進行
2. 過度な共通化
3. シンボリックリンクの使用
4. AIの報告を確認なしで信じる
5. コンテキスト不足での実装依頼
6. 最初から多言語ドキュメント
7. 過度なドキュメント充実化
8. ユニットテスト未完了での統合テスト
```

### 慎重に扱う
```
1. モノレポ構造（拡大しない）
2. GitHub Actions（シンプルに）
3. 共有リポジトリ（作らない）
4. 理想的なシステム（追求しない）
```

## 🎓 学んだ教訓

### 最も重要な教訓
```
「完璧を目指すな、実行せよ」

- シンプルが最高
- 動けば十分
- 段階的に進む
- ユーザーが教えてくれる
```

### AIとの協働の教訓
```
「AIを信じるな、確認せよ」

- 実装報告 ≠ 実際の実装
- コンテキスト管理が重要
- 小さな単位で依頼
- 必ず動作確認
```

### プロジェクト管理の教訓
```
「1つを完成させよ」

- 同時進行は失敗の元
- 依存関係を理解する
- まずは基盤を固める
- 成功してから拡大
```
