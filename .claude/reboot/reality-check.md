# Reality Check - 現実確認

作成日: 2025-11-14

## 🚨 重要な認識

### 既存のテストが通っても喜べない

```
cargo test --workspace
→ 29 passed; 0 failed

しかし、これは：
❌ 正しい仕様に従ったテストではない可能性
❌ 正しい仕様に従った実装ではない可能性
❌ 「嘘のテストが嘘の実装をテストしている」だけかもしれない
```

### user-reflection.mdの教訓

**AIの実装嘘問題**:
- 「実装した」 ≠ 「動く」
- 「実装した」 ≠ 「正しい仕様に従っている」
- AIの報告を信じない

**コンテキスト管理の失敗**:
- コンテキスト不足での実装依頼
- 実装漏れ、仕様外の実装
- 品質低下

### clean-slate-plan.mdの方針

```
「reboot以外の既存ファイルは信じない」
「中途半端である前提で考える」
「ドキュメントも嘘だと疑う」
「どこまでが真実かを考える」
```

## 📋 何を信用できるか？

### ✅ 信用できるもの

```
1. Rustコンパイラが通る
   → 少なくとも文法は正しい

2. 基本的なビルドができる
   → 依存関係は解決している

3. CLIが起動する
   → 最低限の動作はする
```

### ❌ 信用できないもの

```
1. 既存のテストが正しい仕様を表している
   → テストケースが不十分、間違っている可能性

2. 既存の実装が正しい仕様に従っている
   → 実装が不完全、間違っている可能性

3. 既存のドキュメントが正確
   → ドキュメントが古い、嘘の可能性

4. 機能が仕様通りに動作する
   → 「動く」 ≠ 「正しく動く」
```

## 🎯 これから何をすべきか

### Phase 1: 仕様の再定義（最優先）

```markdown
1. README_ja.mdだけを見る（他は無視）
2. 「何ができると書いてあるか」を列挙
3. 「本当にできるか」を1つずつ確認
4. できることだけを新しい仕様書に記録
5. できないことは「TODO」に記録
```

### Phase 2: 真実の特定

```markdown
1. 仕様書に書いたことを実際に試す
2. 試して成功したものだけを「確認済み」とマーク
3. 失敗したものは仕様書から削除して「TODO」へ

例：
「JSON差分が取れる」と書いてある
→ 実際に試す
→ 成功 → 仕様書に✓
→ 失敗 → TODOへ移動
```

### Phase 3: テストの再構築

```markdown
1. 仕様書の「確認済み」機能だけをテスト
2. 既存のテストは参考程度
3. 新しいテストを1つずつ書く
4. 通ったテストだけを残す
```

### Phase 4: 実装の修正

```markdown
1. テストが通らない機能を修正
2. 小さな単位で修正
3. 修正したら即テスト
4. 通ったら仕様書に✓
```
