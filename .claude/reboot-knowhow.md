# リブートのノウハウ

作成日: 2025-12-11
対象: diffx-core, diffx-cli のリブート完了時点

## 1. リブートの前提

**「疑って、確認して、記録する」**

- 既存のテスト ≠ 正しい仕様
- 既存の実装 ≠ 正しく動く
- 既存のドキュメント ≠ 本当にできる

## 2. 正しい順序

```
1. 実際に動かして真実を確認
2. 仕様書を作成（docs/specs/）
3. 仕様書に基づくテストを作成
4. テストが通るように実装を修正
5. ドキュメント（README等）を仕様書に合わせて修正
```

**アンチパターン**:
- ドキュメントを先に書く → 嘘だらけになる
- 既存テストを信じる → ハリボテを検証するだけ

## 3. 仕様書の作り方

1. **CLIを実際に実行**して動作を確認
2. **終了コード**を明確に定義（0, 1, 2, 3...）
3. **出力形式**を厳密に記述（記号、インデント、色）
4. **オプション**の動作を網羅

成果物: `docs/specs/cli.md`, `docs/specs/core.md`

## 4. テストの作り方

### Spec-based tests（内部検証用）
- 仕様書の各項目に対応するテストを作成
- `tests/spec/` に機能別に分類
- 例: `exit_codes.rs`, `formats.rs`, `options.rs`

### trycmd tests（ドキュメント兼用）
- Markdownファイルがテストかつドキュメント
- `tests/cmd/*.md` に配置
- 実際のコマンド出力を記述 → CI で検証される
- 嘘のドキュメントが物理的に作れない

```markdown
# 見出し（説明）

実行例:
```console
$ diffx file1.json file2.json
? 1
~ key: "old" -> "new"
```
```

`? 1` = 終了コード1を期待

## 5. 削除すべきもの

- 古いテスト（仕様と無関係に書かれたもの）
- examples/ ディレクトリ（検証されない嘘の温床）
- 古い計画書（実行済み or 陳腐化）
- マーケティング資料（半年で陳腐化する）

## 6. 残すべきもの

- `docs/specs/` - 仕様書（単一の真実）
- `tests/cmd/` - 検証されるドキュメント
- `.claude/tasks.md` - 現在のタスク
- `CLAUDE.md` - 開発ルール（最小限に）

## 7. npm/pip パッケージのリブート時

diffx-js, diffx-python は CLIラッパーなので:

1. まずCLI（Rust）のリブートを完了させる
2. ラッパーは CLI の仕様書を参照
3. ラッパー固有のテスト（インストール、パス解決等）を追加
4. README は CLI の README を翻訳ベースに

## 8. 時間の目安

- 仕様書作成: 1セッション
- テスト作成: 1セッション
- ドキュメント修正: 1セッション
- クリーンアップ: 1セッション

合計: 4セッション程度（1セッション = コンテキスト1回分）
